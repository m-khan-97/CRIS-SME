# IoMT Control Matrix

The table below summarises the ten CRIS-IoMT controls and the specific review question for each control.

| Control | Purpose | Cloud evidence | External evidence needed | Candidate DSPT / CAF mapping | Expert review question |
| --- | --- | --- | --- | --- | --- |
| `IOT-001` Cloud device-identity registration posture | Assess cloud-side device identity registration governance. | IoT Hub inventory, device identity inventory, authentication metadata where available, certificate authority configuration where available. | Device-side credential storage, firmware trust anchor validation, clinical device ownership and lifecycle process. | DSPT `B2.a`; CAF B2. | Is device identity inventory a meaningful healthcare IoT assurance signal when bounded to cloud registration and authentication metadata? |
| `IOT-002` Shared access policy and key exposure risk | Assess least-privilege posture of IoT Hub shared access policies. | Shared access policies, policy rights, custom policy count, default policy exposure. | Application usage of shared access policies, secret rotation process, break-glass procedure. | DSPT `B2.a`, `B3.a`; CAF B2. | Are overbroad shared access policies a valid healthcare IoT governance risk? |
| `IOT-003` IoT telemetry diagnostic logging | Assess whether cloud telemetry diagnostics support investigation. | IoT Hub diagnostic settings, Log Analytics, Event Hub, Storage destinations, enabled categories. | SOC review process, clinical incident investigation workflow. | DSPT `C1.a`; CAF C1. | Is diagnostic setting coverage sufficient evidence for a cloud governance monitoring control? |
| `IOT-004` IoT security monitoring and Defender coverage | Assess whether IoT security monitoring evidence is observable. | Defender for IoT where accessible, Defender for Cloud recommendations, security alert integration. | SIEM triage process, clinical operations escalation path, monitoring runbooks. | DSPT `C1.a`, `C2.a`; CAF C1, C2. | Is it defensible to report unavailable Defender/equivalent monitoring as an observability gap rather than a definitive failure? |
| `IOT-005` Public network exposure of IoT ingestion endpoints | Assess public exposure of managed IoT ingestion paths. | IoT Hub public network access, firewall rules, allowed IP ranges, private endpoint state. | Remote-care access requirement, network architecture review, third-party connectivity evidence. | DSPT `B4.a`; CAF B4, B5. | Is public IoT ingestion exposure a valid risk signal when intentional-public exceptions require manual review? |
| `IOT-006` Conditional private endpoint and network isolation posture | Assess uncompensated public ingestion when private connectivity is absent. | Private endpoint inventory, connection state, public network access, IP filter evidence, certificate-authority evidence. | Network segmentation design, clinical network dependency review, accepted public-ingestion design evidence. | DSPT `B4.a`, `B5.a`; CAF B5. | When should private endpoint absence be treated as a risk versus an accepted architecture decision? |
| `IOT-007` Telemetry storage and retention governance | Assess whether telemetry is routed to governed destinations. | IoT message routes, storage destinations, retention settings where available, lifecycle policy signals. | Clinical record retention policy, privacy impact assessment, data minimisation justification. | DSPT `B4.b`; CAF B4, D1. | Is telemetry routing to governed storage a useful assurance signal if privacy and clinical-record interpretation stay manual? |
| `IOT-008` Key Vault and secret management for IoT integrations | Assess governed secret handling for IoT integrations. | Key Vault inventory, purge protection, private endpoint posture, secret/key metadata where available. | Application secret usage, rotation approval evidence, third-party supplier handling. | DSPT `B2.a`, `B4.b`; CAF B2, B3. | Is managed-secret posture a credible proxy for IoT integration credential governance? |
| `IOT-009` Incident detection and alerting coverage | Assess whether IoT-specific alerts are deployed and routed. | Azure Monitor alert rules, Log Analytics workspace, diagnostic settings, action groups. | Incident response runbook, clinical escalation process, SOC operating model. | DSPT `C1.a`, `D1.a`; CAF C1, D2. | Is a deployed IoT-specific Azure Monitor alert a sufficient cloud-side signal for detection readiness? |
| `IOT-010` Evidence sufficiency and clinical safety boundary | Prevent cloud evidence from being misread as clinical/device assurance. | Evidence class counts, unavailable signal counts, device-required evidence paths, report caveats. | Clinical safety case, medical-device safety review, biomedical engineering validation, operational acceptance. | DSPT `A2.a`, `D1.a`; CAF A1, A2. | Does this explicit boundary control make the paper more defensible? |
